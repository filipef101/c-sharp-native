## One changing tap, one file write

After the ten no-op renders, one `save` press. `tap-single-begin`, then one `state-save-us=575`. The no-op renders did not write, because the queued bytes matched the file already written at startup (`state-save-us=695`). The worker writes the newest snapshot once. A second write of the same bytes is skipped.

The save press is `steps=3` and includes `clipboard-ok`. `action-us=10389`, `vm=9596`. That vm time is the handler before `RequestRender`, not the steps=1 path.
