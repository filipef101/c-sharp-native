## RequestRender only, listener

`--es nativepoc_bench tap10`. pid 7727. `IsDynamicCodeSupported=False`. Ten `RecordProgram.RunRenderRequest` calls (`steps=1`), posted 40 ms apart so the UI thread can return. The counter record was already bound by the first frame (`prep=84` on that cold frame, including decode).

`action-us` samples, in order: 3513 72352 340 209 197 192 205 196 182 188. p50 201.0 µs.

One yielded frame, the first tap: `frame-wait-us=7425`, logged after `action-us`. The other frame callbacks were delivered together after a stall, so those waits include the stall. They are not inside `action-us`.

The 72352 µs sample is `dir=69718` inside `ApplyDirection`. It is one stall, not the median. `dir` p50 is 9.0 µs.

Steady tap, `action-us=192`: `input=5 vm=9 prep=19 render=118 tail=78`. `prep` is inside `render`. `vm + render + tail` is the action. There is no separate 3 ms bucket inside the action on this pid.

Phase p50 for those ten taps: eval 21.0, diff 6.0, reconcile 0.0, layout 17.5, invalidate 5.0, paint 0.0, book 0.0, prep 17.5, dir 9.0, content 0.0, title 0.0, focus 0.0, log 14.0, after 23.0, save 0.0. `after` is dir + content + title + focus + log. `save` is 0 because the file write is no longer inside `RenderNow`.

A cold `Bind` on the first frame was 84 µs of `prep`. That does not account for an older 4665.5 µs `action-us`. This steps=1 path does not reproduce that number. The older phase sum was a text-changing render. This path's tree does not change (`reconcile` p50 0.0). Unverified that the two clocks were the same work.

## One changing tap, one file write

After the ten no-op renders, one `save` press. `tap-single-begin`, then one `state-save-us=575`. The no-op renders did not write, because the queued bytes matched the file already written at startup (`state-save-us=695`). The worker writes the newest snapshot once. A second write of the same bytes is skipped.

The save press is `steps=3` and includes `clipboard-ok`. `action-us=10389`, `vm=9596`. That vm time is the handler before `RequestRender`, not the steps=1 path.

## Paint, log, and the configuration read off the tap

Emulator-run. Same boot `56815464-4bc4-4f4c-a503-944cb91ab31f`. Hyndman-Fan type 7. n=10. Nothing dropped. Host load is the 1-minute load from `/proc/loadavg`.

The 18668 µs `paint` on pid 16001 was the first `ThemeRuntime.Paint` inside the tap. The bench now paints once before the series, and a later frame skips `SetTextColor` and `SetBackgroundColor` when the cached page color and text color match. `paint-ran=0` and `paint=0` on every timed sample below.

The phase line and the `rendered count` line are formatted after `clock.Stop`. `phaselog-us` is that log I/O. It is not inside `action-us`. `gc0` is `GC.CollectionCount(0)` across the render. A gen0 collection increments it. The timed samples below are `gc0=0`.

`ThemeRuntime.IsDark` used to read `Resources.Configuration.UiMode` on every frame. On pid 18190, before that read was cached, one of the ten taps was `theme=35160` inside `action-us=35731`. `Load` now reads the night bit once. A later tap reads the cached bit. `theme` on the series below is 0 or 1.

`GC.Collect(0)` runs before the warmup renders. Eight warmup renders run, then one frame, then four more warmup renders, then the first timed `RequestRender` in that same turn. The other nine are posted 40 ms apart. The first posted callback on the previous binary (pid 18259) waited in `prep` for 16845 µs with `bind=hit` and `gc0=0`. That wait is the lock around `ScreenNav.Top`, after the frame callback returned. It is not in this series.
